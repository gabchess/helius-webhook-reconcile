# Helius triage

One path: ticket "my webhook stopped", then the diff, then a drafted reply that a person reviews. Never send the draft without reading it.

The reply is not generated by a model and it is not retrieval. Every fact in it comes from the diff report, and every quote in it is a whole sentence copied from `fixtures/helius-faq-webhooks.md`, a snapshot of https://www.helius.dev/docs/faqs/webhooks.md (source URL and fetch date in its first line).

## Steps

1. Get two files. Stop and ask the customer if either is missing.
   - Received: the signatures their endpoint logged, as JSON (a bare array of `{signature}` rows, or `{ "payloads": [...] }`).
   - Reference: `getTransactionsForAddress` for the webhook address over the same window. Use `--live-reference` with a window, or a saved response with `--reference`.
2. Run the diff with `--json`. Exit code 1 only means events are missing.
   ```
   webhook-reconcile diff --received received.json --reference reference.json --received-tag "run live" --reference-tag "run live" --json > report.json
   ```
   A file with no `tag` of its own has unknown origin, and the draft then ends in `NEEDS HUMAN`. The two tag flags are your word about where a file came from. Pass `--received-tag "run live"` only when the received file is the customer's real endpoint log. Pass `--reference-tag "run live"` only when the reference file is a real saved `getTransactionsForAddress` response, and drop it with `--live-reference`, which the tool tags `run live` itself. Allowed values are `run live`, `mocked` and `litesvm`. A file whose own tag differs from the flag is an error.
   Add `--backfill-out backfill.json` with `--refetch-from` or `--live` to put a backfill count in the report.
3. Save the ticket text to `ticket.txt` and draft the reply.
   ```
   helius-triage --ticket ticket.txt --report report.json
   ```
   Exit 0 prints a draft. Exit 1 prints `NEEDS HUMAN: <reason>` and means a person reads the ticket first. Exit 2 is bad input.
4. Read the draft against the report. Check the line `Data used: reference ..., received ...`. If either side is not `run live`, the draft opens with "I compared the reference and received signature sets in this report", says the gap is a test of the tool and not a confirmed loss, and makes no retry, permanent-loss, endpoint or backfill claim. Keep those lines.
5. Send nothing until you have checked the signatures against the customer's window.

## What the draft says

| Report | Draft |
| --- | --- |
| Never-received rows that did not fail on chain, both tags `run live` | Lists up to three signatures and asks the customer to confirm the webhook type and filters. Only if they match, it quotes the retry policy and the permanent-loss sentence, and offers a backfill. It does not claim that Helius attempted delivery or used up its retries |
| The same rows, either tag not `run live` | Lists the set difference only: "the reference holds N transactions that the received set lacks". No retry, loss, endpoint or backfill claim |
| No such rows, both tags `run live` | "Nothing is lost in this window." No retry quote. If only failed rows are missing, it says "No successful transaction is missing in this window." instead |
| No such rows, either tag not `run live` | "In this data set nothing is missing. That is not proof that nothing was lost on your webhook." |
| A tag that is missing or not one of the three | `NEEDS HUMAN`, exit 1. The draft never guesses where data came from |
| Signatures received more than once | Says they were seen, and quotes the FAQ on the possible causes and on dedupe |
| Never-received rows that failed on chain | Says an enhanced webhook never sends them and a raw webhook does send failed transactions, so for a raw webhook it asks the customer to confirm its filters before treating them as missing, and quotes the FAQ |
| Received signatures outside the reference window | Asks to widen the window before concluding |

Failed rows are never listed as lost, whatever `--status` the diff ran with. The draft names the webhook type that decides whether they were missing.

## The AI flag

Off by default. `helius-triage --ai` asks the TypeSafe Jev model one question: is this a webhook delivery ticket? The answer only decides whether to draft. A different kind, or a confidence below 0.60, gives `NEEDS HUMAN`. The model never writes or edits the reply.

The model never sees the ticket text. The request carries `ticket_words`: the words of the ticket that are in `JEV_WORDS`, a fixed, sorted support vocabulary in `crates/webhook-reconcile/src/triage.rs`. The ticket is lowercased and split on anything that is not a letter a to z, and each word found in the list is replaced by the constant from the list. Every other word is dropped, and no other text from the ticket is sent, so no byte of the request is copied from the ticket. A name, a digit string, a token or a password that is not in the list cannot be sent. A secret reaches the model only if it is itself a vocabulary word. `a_letters_only_secret_and_every_probe_secret_are_absent_from_the_request` proves that `huntertwo` and the probe secrets are absent, and `each_request_word_is_a_constant_from_the_vocabulary` proves every request word is a list constant. A person still reads the ticket before anything is sent. The keyword rules of the default path read the full text locally.

- `--ai --jev-from fixtures/jev-classify-mocked.json` replays the hand-built mocked Jev fixture, offline. The fixture is `mocked`: built by hand from the documented response shape, not recorded from a live call.
- `--ai` alone calls the live API and reads `TYPESAFE_API_KEY` from the environment. That path is not run in this repo's tests.
- With the flag off, keyword rules decide, no key is read and no model is called. `triage_flag_off_calls_no_model` proves it with a recording fake.

## Limits

- It does not call Helius for you unless you pass `--live-reference` or `--live`.
- It cannot say why the endpoint failed. The draft says only that the endpoint "may have" returned an error or timed out, that the customer's log may have missed the events, or that the webhook may have been disabled.
- Helius disables a webhook on its own when the delivery failure rate is high. The FAQ snapshot says so in its answer to "Why was my webhook automatically disabled?" (`fixtures/helius-faq-webhooks.md`, line 88: "automatically disables webhooks with a ≥ 95% delivery failure rate"). The draft paraphrases that and tells the customer to check the dashboard. It is not one of the verbatim quotes.
