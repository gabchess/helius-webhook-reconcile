# Helius triage

One path: ticket "my webhook stopped", then the diff, then a drafted reply that a person reviews. Never send the draft without reading it.

The reply is not generated by a model and it is not retrieval. Every fact in it comes from the diff report, and every quote in it is a whole sentence copied from `fixtures/helius-faq-webhooks.md`, a snapshot of https://www.helius.dev/docs/faqs/webhooks.md (source URL and fetch date in its first line).

## Steps

1. Get two files. Stop and ask the customer if either is missing.
   - Received: the signatures their endpoint logged, as JSON (a bare array of `{signature}` rows, or `{ "payloads": [...] }`).
   - Reference: `getTransactionsForAddress` for the webhook address over the same window. Use `--live-reference` with a window, or a saved response with `--reference`.
2. Run the diff with `--json`. Exit code 1 only means events are missing.
   ```
   webhook-reconcile diff --received received.json --reference reference.json --json > report.json
   ```
   Add `--backfill-out backfill.json` with `--refetch-from` or `--live` to put a backfill count in the report.
3. Save the ticket text to `ticket.txt` and draft the reply.
   ```
   helius-triage --ticket ticket.txt --report report.json
   ```
   Exit 0 prints a draft. Exit 1 prints `NEEDS HUMAN: <reason>` and means a person reads the ticket first. Exit 2 is bad input.
4. Read the draft against the report. Check the line `Data used: reference ..., received ...`. If either side is `mocked` or `litesvm`, the draft says the gap is a test of the tool and not a confirmed loss. Keep that line.
5. Send nothing until you have checked the signatures against the customer's window.

## What the draft says

| Report | Draft |
| --- | --- |
| Never-received rows that did not fail on chain | Lists up to three signatures, quotes the retry policy, says they will not arrive again, offers a backfill |
| No such rows | "Nothing is lost in this window." No retry quote |
| Signatures received more than once | Says they were seen, and quotes the FAQ on the possible causes and on dedupe |
| Never-received rows that failed on chain | Says they are not lost events and quotes the FAQ: enhanced webhooks do not send failed transactions, raw webhooks do |
| Received signatures outside the reference window | Asks to widen the window before concluding |

Failed rows count as not lost whatever `--status` the diff ran with.

## The AI flag

Off by default. `helius-triage --ai` asks the TypeSafe Jev model one question: is this a webhook delivery ticket? The answer only decides whether to draft. A different kind, or a confidence below 0.60, gives `NEEDS HUMAN`. The model never writes or edits the reply.

- `--ai --jev-from fixtures/jev-classify-mocked.json` replays the hand-built mocked Jev fixture, offline. The fixture is `mocked`: built by hand from the documented response shape, not recorded from a live call.
- `--ai` alone calls the live API and reads `TYPESAFE_API_KEY` from the environment. That path is not run in this repo's tests.
- With the flag off, keyword rules decide, no key is read and no model is called. `triage_flag_off_calls_no_model` proves it with a recording fake.

## Limits

- It does not call Helius for you unless you pass `--live-reference`.
- It cannot say why the endpoint failed. The draft says "likely".
- Helius disables a webhook on its own when the endpoint failure rate is high (Toggle Webhook docs). The draft tells the customer to check the dashboard. This is not a quote and is not in the FAQ snapshot.
